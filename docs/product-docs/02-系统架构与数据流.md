# 02 · 系统架构与数据流

> 出处：`CONTEXT.md`、`weflow/docs/deployment-guide.md`、`weflow/docs/technical-documentation.md`、

## 1. 总体拓扑

单机部署形态（开发机与 X230 生产机同构，仅服务托管方式不同）：

```
                ┌────────────────────────── Windows 服务器 ──────────────────────────┐
                │                                                                     │
  浏览器/桌面端 ─┼──▶ core-api (3100) ── 静态托管 support-web/dist（SPA + /api 同源）   │
  手机端(公网)  │      │  │                                                            │
                │      │  ├── PostgreSQL 16 (5432)   ← 唯一业务事实源                  │
                │      │  └── Redis 7 (6379)         ← BullMQ 队列 + 事件扇出 pub/sub  │
                │      ▼                                                              │
                │  agent-worker (3101 健康探针) ── Agent Turn / 记忆捕获               │
                │  ingestion-worker (3102 健康探针) ── 图片描述 / 语音转写             │
                │                                                                     │
                │  channel-host-wechat (43123, 本机回环, 登录用户会话) ◀── 微信桌面版   │
                │      直读微信加密 DB + UIA 自动化发送（不可服务化）                  │
                │                                                                     │
  公网入口 ─────┼── frpc 隧道 → 自建 frps(38.22.235.27:7000) + caddy → *.leaif.com     │
                └─────────────────────────────────────────────────────────────────────┘
```

外部 Provider（系统之外，可替换）：DeepSeek（决策模型）、小米 MiMo（视觉）、
硅基流动（ASR / Triage / FAST 小模型）、WeKnora（知识库）、Expo（推送通道）、DiceBear（预设头像）。

## 3. 消息主链路（入站 → 回复）

```
微信客户端
   │ 读 DB / GUI 自动化（channel-host-wechat，Python + SQLite event store）
   ▼
Channel Host HTTP (127.0.0.1:43123, Bearer token)
   │ GET /api/v1/channel/events      入站事件轮询（core 500ms 间隔，eventId 幂等）
   │ POST /api/v1/channel/send       出站发送操作（operationId 幂等，5 态回执）
   │ GET /api/v1/channel/media/:ref  媒体流（X-Media-Variant: original|thumbnail）
   │ GET /api/v1/channel/contacts    联系人分页同步
   ▼
Core API (3100)
   │ ingest 幂等入库 → conversations/messages；媒体建 media_assets(queued)
   │ turn admission 合并窗口（基准 12s；「半句启发式」判定话没说完则延长至 30s，
   │   判定规则见 06 章 §2）→ dispatcher CAS 认领建 1 个 Turn
   │ outbound poller 对账 send operations → 8 态发送状态回写 messages
   ▼
agent-worker（BullMQ agent-turns）
   │ Triage 分流 → 上下文装配（事实卡/记忆/轮窗/原文窗口/档案）
   │ 模型调用（thinking 保留，180s 决策超时）→ 决策 JSON → 策略闸门
   │ 工具检查点（retrieve_knowledge 等）→ 证据回喂 → 续步（ReAct）
   ▼
回复分段落库（reply_batch_id + sequence）→ send operations → channel-host 发送
   │
   ├── 记忆捕获：90s 安静窗口 → 提取长期记忆（agent-worker memory-capture 队列）
   └── 知识检索：WeKnora Provider（设置中心「知识库连接器」30s 热生效）
```

**关键设计不变量**（`core/AGENTS.md`）：

1. PostgreSQL 是唯一持久业务事实源；Redis/BullMQ 作业只是**可恢复的投递提示**（丢了可从 PG 重建）。
2. 先事务落事实，再入队/发送；一切跨进程并发用稳定 ID + 幂等键 + 乐观锁（conversation revision、
   handoff revision、tool lease、CAS 状态机）。
3. 只合并**排队中**的 Turn，绝不取消在途模型请求。
4. 模型响应只是草稿；投递必须走持久化 operation ID 并对账 `unknown`（不可静默改写）。
5. 前一批回复 pending/submitting/unknown 时不处理该会话的下一个 Agent Turn（会话内串行，会话间并行）。

## 4. 出站发送状态机（两层词表）

**Host 侧 5 态**（`@weflow/contracts` CHANNEL_PROTOCOL v6）：
`pending → executing → confirmed | unknown | failed`（`inFlightSendOperationStates = pending|executing`）。

**Core 侧 8 态**（`messages.send_state`，唯一权威 `core/modules/conversations/application/send-states.ts`，
迁移 0080 起 CHECK 约束）：

```
pending → submitting → observed → confirmed
                     ↘ failed
unknown（对账无法确认，前端必查证）
held（**两个来源**：① 发送期插话闸门扣留，send_error='customer_interjection'；
② Kill Switch「AI 自动应答」关闭时的拦截。两者均为终态，开关恢复后**不自动补发**）
cancelled（原 cancelled_handoff / cancelled_policy 已合并，原因在 send_error）
```

Host 5 态在 `sendStateFromHost` 恰好映射一次（`executing ≡ submitting` 在途）。

> **客户端投影词表**：三端 UI/接口展示用的 `outcome` 8 值
> （`pending/accepted/sent/failed/unknown/held/cancelled/not_found`，见 05 章 §14）
> 与上面的权威 8 态是映射关系：`accepted ≈ submitting`（已受理在途）、
> `sent ≈ confirmed/observed`（已送达）、其余同名直映；`not_found` 是**带外值**
> （clientRequestId 查无记录，不是发送状态）。

## 5. 实时事件扇出（ADR-0009）

- 发布（两个 worker + api 自身）：`publish = 本进程即时投递 + Redis pub/sub 广播`
  （频道 `weflow:conversation-events`），信封带每进程 origin UUID 防回环。
- 订阅：api 进程 subscribe 后经 **SSE** `GET /api/v1/console/events/stream` 推给网页端/手机端。
  事件负载为轻量信封 `{ type, conversationId, occurredAt, messageId? }`（不含消息正文——
  客户端收到即回拉权威数据）；线上广播额外附 `origin`（进程 UUID）用于回环去重，
  **不投递给消费端**（`conversation-events.ts`）。
- **事件只是失效信号，不是事实来源**：客户端收到即回拉权威状态（SSE 白名单 11 类事件，
  250ms 尾沿合并），另有轮询兜底（网页端 15s 对账/5s 兜底；手机端详情 30s/列表 60s）。
- Redis 不可用自动降级为进程内投递（单进程部署时功能完整）。
- 消费端白名单：`customer_message / agent_message / human_message / handoff_created /
  handoff_claimed / handoff_transferred / handoff_finished / ownership_changed / brief_updated /
  conversation_updated / reply_interrupted`（发送期插话闸门扣留批次必须进白名单，否则消息"莫名消失"）。

## 6. 队列与后台任务全景

BullMQ 队列（统一工厂 `infrastructure/redis/job-queue.ts`：attempts=3、指数退避 2s 起、
removeOnComplete=100、removeOnFail=500；作业信封带 jobId/jobType/ownerModule/businessEntityId/
idempotencyKey/attempt/traceId）：

| 队列 | 生产者（dispatcher 在 api 进程） | 消费者 |
|------|------|------|
| `agent-turns` | agent-turn-dispatcher | agent-worker |
| `memory-capture` | memory-capture-dispatcher | agent-worker |
| `media-processing` | media-processing-dispatcher | ingestion-worker |

api 进程常驻后台任务（`core/apps/api/main.ts` start 钩子）：conversation event bus、
mobile handoff maintenance、turn-admission / scheduled-send / session-wake / handoff-reminder /
expo-push 各 dispatcher、memory maintenance、Channel Host 四轮询器（event/outbound/media/contact）、
outbound 发送循环、syncChannelMedia、upgradeChannelImageOriginals、syncChannelContactProfiles。

## 10. 模块边界一句话

- **Channel Host 拥有**：通道传输事实（登录、入站事件、通道媒体、发送、投递确认）。
- **Core 拥有**：业务事实（会话、消息、Turn、Handoff、联系人档案、记忆、媒体元数据、审计）。
  Core 只通过 `channel.events / channel.send / channel.media / channel.contacts` 四个正式能力
  与 Channel Host 通信，**不读通道私有 DB、不理解 `local_id`**。
- **客户端（support-web/mobile）不拥有业务状态**，不得绕过 Core API。
- 三条红线：不得把业务逻辑移进 Channel Host；不得把 Redis 队列当事实源；
  不得从 UI 状态/未读数/分页推断入站消息。

## 11. 容量与限制（设计边界）

Weflow 是**单机单实例**产品（无水平扩展设计；「单进程部署」是卖点也是边界）：

| 维度 | 边界/默认 | 出处与说明 |
|------|-----------|-----------|
| 部署规模 | 单台 Windows 服务器；一个 Core + 一个共享工作空间 + **一个 Channel Host 端点**（Core 只有单个 `CHANNEL_HOST_BASE_URL`，未实现一 Core 挂多 Host） | 多微信账号的正确形态 = 每台机器一套完整栈（Core+Host 各一，账号维度字段保证未来数据可合）；ADR-0005 的 `account` 是**数据隔离**维度，不是单机多实例编排 |
| 用户规模 | 封闭发放账号的内部团队（无注册开放） | `create-user.js` 逐个发放 |
| Agent 并发 | `AGENT_WORKER_CONCURRENCY` 1–20（默认 3）；同会话串行、跨会话并行 | 会话级互斥由队列与 DB 状态机保证 |
| 记忆/媒体并发 | `MEMORY_CAPTURE_CONCURRENCY` ≤5（默认 1）、`MEDIA_PROCESSING_CONCURRENCY`（默认 1，防多模态端点过载） | config.ts |
| 上传/媒体上限 | 人工上传 ≤100MB（multipart）；Host 媒体 >25MB 拒收（413）；图片描述输入 >10MB 回退缩略图；知识代理上传 ≤25MB（`MAX_KNOWLEDGE_UPLOAD_BYTES`，代码常量） | media 模块 / 通道协议 / boundary.ts |
| fetch_url | 响应体 ≤256KB、正文截 8000 字、15s 超时、仅公网 http(s)（见 14 章 SSRF 防线） | execute-tool-plan.ts |
| 数据保留 | **消息/媒体/审计无自动删除或归档机制**——只增不减；磁盘与库容量规划是部署方责任 | 备份策略见 13 章 §4.3 |
| Redis 数据 | 队列与 pub/sub 均可从 PG 重建（非事实源），Redis 丢失 = 丢投递提示，不丢业务事实 | core/AGENTS.md |
| 定时类语义 | 定时发送 `send_at`、静音时段 22:00–08:00、会话 TTL 等全部按**服务器本地时间**解释（JS Date，无时区字段）——跨时区部署须统一服务器时区 | scheduled-sends.ts 无任何时区处理 |
| 观测上限 | 无内置 metrics/APM/告警系统（现状，见 §12）；并发 SSE 连接数未做专门限制 | RELIABILITY-PLAN（未动工）规划环境态降级上报与哑火告警 |
| 吞吐基线 | **无正式压测数据**。实测经验值：单次模型调用 87–246ms、Turn 端到端 10–24s（瓶颈在管线排队与通道，不在模型，见 06 章 §11）；当前生产（X230，i5-3320M）运行于小团队真实规模 | THINKING-PIPELINE-PLAN B0 探针 |

## 12. 可观测性（现状）

**有什么**：

- **结构化日志**：pino（`LOG_LEVEL` 控制）；三进程日志位置见 13 章 §1（dev `core/.dev-logs/`、
  WinSW `tools/winsw/logs/` 10MB×8 滚动、X230 `C:\We\logs\`）。
- **Turn 级审计轨迹**：`agent.turns`（status/model/error_code/trace_id/时间戳）+
  `agent.turn_events`（阶段事件）+ `tool_executions`（参数/结果）；`model_call` 事件带
  usage/latencyMs/finishReason，`model_reasoning` 事件带 ≤8k 字符思维链草稿。
- **串查入口**：support-web 决策轨迹抽屉（`GET /api/v1/agent/decision-trace/:turnId`）、
  系统状态页最近 Turn 诊断（`GET /api/v1/admin/agent-turns`）、轮次体检与 live-turn 投影端点；
  `messages.trace_id` / `turns.trace_id` 可在库层面把消息与 Turn 关联。
- **健康探针**：`/health/live`、`/health/ready`（503 = 依赖异常）；channel-host `/api/v1/status`
  （host_alive / wechat_process_alive / db_readable）与 weflowctl doctor 七类体检。

**没有什么**（诚实声明）：

- `trace_id` 有落库与展示，但**未打通到日志行**（pino 行内无 trace_id 字段）——跨进程串查
  目前靠 Turn/消息 ID 在库与界面层完成。
- 无 metrics 抓取（Prometheus 等）、无告警通道、无分布式追踪。「哑火告警」「轮次时间线分段
  耗时」在 RELIABILITY-PLAN 中规划（未动工）。
- 排障依赖：决策轨迹 + doctor + 日志 + `x230-deploy/` 诊断脚本箱（13 章 §5）。
