# Mobile UI 与交互规格

Mobile 是面向内部客服的移动值班台，不是缩小版后台，也不是普通聊天页。界面始终优先回答：哪些会话需要处理、哪些由我负责、客户刚说了什么。

## 设计哲学

Mobile 应像专业人士每天使用的高级移动应用，而不是管理后台。整体体验接近 Apple Mail、Things 3 或 Linear：清晰、克制、可靠、快速。

- 可读性优先于装饰。
- 交互优先于动画。
- 信息层级优先于信息堆叠。
- 平静优先于刺激。
- 操作速度优先于视觉效果。
- 每个动画都必须表达状态变化、反馈或等待过程。
- 每种颜色都必须有明确语义；颜色不能成为唯一状态线索。
- 每次点击都应减少用户判断、输入或导航成本。
- 避免传统企业后台的仪表盘布局、过多卡片、浮动小组件和 AI 中心化视觉。

视觉表达可以有品质感，但不应抢夺会话内容、待办优先级或当前操作的注意力。

## 信息架构

Mobile 只有一个一级工作入口：**Handoff Inbox**。不使用底部导航，也不提供独立待办或知识工作台。

- **等待接手**：Agent 已经请求人工，客服决定是否接手。
- **我处理中**：当前账号已接手的会话，客服继续阅读、回复和结束人工处理。
- **个人入口**：头像进入通知、账号、安全和退出设置；账号页提供「信息名片」入口，客服编辑显示名与擅长领域标签、更换头像并修改密码。
- 已结束周期、Handoff 历史、联系人资料、转交和 Agent 回复质量反馈均为会话内次级功能。
- 知识检索只能从当前会话上下文触发，不允许离开客户问题浏览资料库。

## 信息名片

- 名片是客服对外的自我形象卡：头像（点击更换，方形裁剪）、显示名、擅长领域标签与修改密码入口。显示名输入框带「保存」按钮，未修改时禁用；清空输入 = 清除显示名，回落为登录账号。
- 标签以多选芯片呈现，词表与 Core 专家队列同源（上限 7 个），选中状态用主题蓝高亮；保存后提示「标签已保存」。说明文案明示用途：转人工时系统会按标签把相关任务定向推送给你。
- 标签加载失败显示重试提示，不影响头像与显示名编辑；`agentProfile` 能力缺失时隐藏显示名与标签编辑区。
- 修改密码沿用首次登录页的密码表单，自愿进入时显示返回头、成功后返回名片，不提供退出登录。

## 会话列表

Inbox 使用邮件式分隔列表，不使用巨大卡片。每行只突出联系人、问题摘要、转人工原因和等待时间；底层状态统一映射为 `等待接手` / `我处理中`。

搜索默认收起，点击顶部搜索图标后按联系人、公司或问题摘要搜索；不提供复杂筛选抽屉。

## 会话详情

页面由固定顶部状态栏、聊天时间线和动态底部操作区组成。

- 页面在前台每 15 秒同步一次 transcript、Handoff 和专业协作状态；进入后台停止轮询，回到前台立即同步。同步发现 revision 变化时，已有草稿必须进入 stale 状态。
- 图片消息显示受鉴权的在线图片；加载中、未准备好和加载失败分别给出明确状态，离线时显示“图片需联网查看”。

- 顶部只显示联系人、真正影响当前回复的上下文和工作状态；更多菜单只保留结束人工处理、Handoff 历史与存量协作收尾。
- 时间线明确区分客户、自动 Agent、人工客服、系统与状态事件。客户消息权重最高；人工与 Agent 均可置右侧，但 Agent 使用浅色气泡和“自动”标签。系统及状态事件使用居中时间线，不伪装为聊天气泡。
- 聊天正文前优先显示 Core 返回的 `handoff.briefing`，呈现问题摘要、确认事实、待确认信息、未解决事项、转人工原因和建议首句。客户端不得根据最近消息、风险或 Handoff 原因补写事实；没有服务端摘要时不显示伪摘要。
- 建议首句可由当前负责人一键放入输入框继续修改，但不得自动发送；非负责人只读查看。
- 首屏加载最近 50 条，使用稳定游标向上加载。查看历史时不强制滚动；在底部附近自动跟随新消息，否则显示“有 N 条新消息”按钮。

## 状态驱动的底部操作

| 状态               | 底部内容                                   |
| ------------------ | ------------------------------------------ |
| 无 Handoff         | 只读查看，等待 Core 创建人工请求       |
| `HANDOFF_PENDING`  | 唯一主按钮 `接手处理`                     |
| 本人 `HUMAN_ACTIVE` | 文本输入框、发送、转交处理与结束人工处理  |
| 目标用户 `TRANSFER_PENDING` | `接手处理` 与弱操作 `无法接手`      |
| 其他责任状态       | 明确说明当前负责人或等待队列并保持只读     |
| `HUMAN_FINISHED`   | 显示本次人工处理已结束；不提供“重新打开”   |

结束人工处理使用解释 Human → Agent 语义的单一确认层。接手和普通文本发送不弹确认；转交确认页面本身就是确认，不再追加 Alert。接手成功前不得乐观显示 ownership；冲突后立即刷新并切换真实状态。

## 次级操作

- 输入区 `＋` 只保留 `建议回复`、`转交处理`、`联系人资料`；`转交处理` 再选择具体客服或专业队列。
- `请求协助` 停止创建；存量请求只保留查看、提交意见、关闭和取消，直到清零。
- `结束人工处理` 与 Handoff 历史放在 `···` 菜单。
- 已完成会话不进入一级导航，完成后短暂显示状态并返回 Inbox。

## 会话内知识辅助

知识能力不再拥有一级页面，只在当前 owner 的回复区以轻量建议出现：

```text
主动生成 → 建议回复 → 查看依据 → 采用到 Human Draft → 人工发送
```

界面不暴露独立查询、上下文覆盖、知识托盘、完整结果或多类行动输出。Suggestion 生成失败时只隐藏建议能力，不影响 Brief、Transcript 或 Composer。

- 默认只显示建议回复和“依据 N”入口；无知识证据的会话衔接建议显示“依据当前会话”。
- 采用建议只写入输入框，永远不自动发送。
- Suggestion 与 Human Draft 是不同对象；revision 变化后 Suggestion 只能重新生成，已采用且编辑过的 Draft 才可在检查最新消息后继续使用。
- FAQ、Wiki、收藏、最近使用、快速/深度检索和独立知识历史不在 Mobile 暴露。

## 草稿与最新内容检查

- 可发送草稿只属于当前会话负责人，并绑定当前 `handoffId`；非负责人不显示可编辑输入框。
- 会话出现新消息后，草稿显示“会话已有新内容，请先检查”。
- 不使用普通确认弹窗直接继续；客服必须查看新内容，或明确点击“已检查最新内容，继续使用草稿”。
- 继续使用后记录 `reviewedAtRevision`，服务端校验通过后才允许发送。
- 切换账号时原账号草稿隐藏并锁定，重新登录原账号可恢复；转交后的草稿显示为“转交前草稿，仅供查看”。

## 发送与失败反馈

发送后立即显示本地消息气泡及“发送中”。后续由服务端状态更新为“已受理/排队中”“已发送/平台已接收”或失败。失败必须区分可重试、服务端拒绝、权限已失效和结果未知；结果未知时只能先查询原请求的服务端结果，不显示“重新发送”按钮。若底层渠道无法证明客户设备收到，禁止显示“已送达”。失败状态显示在对应气泡下方；重试复用原 `clientRequestId`，不新增气泡。

首版仅支持人工文本发送和客户图片查看。消息提交后不提供编辑或撤回。

## Handoff 与 Inbox 体验

Handoff 历史从更多菜单进入，以周期时间线展示负责人、状态、开始/结束时间、时长及可选内部摘要。等待接手和我处理中是 Inbox 的唯一两个工作分段。

高风险、优先级和超时阈值由 Core 计算或配置，客户端只负责呈现。

## 通知、空状态与视觉风格

通知点击后始终重新请求会话，再按最新归属和状态渲染页面。默认 Push 仅显示联系人和状态；用户可在设置中启用预览或完全隐藏内容。

无等待接手、无本人负责会话、离线和 Token 失效均须有明确状态。离线 owner 保留 Composer 并可编辑安全草稿，显示“离线 · 草稿已保存在本机”；发送、接手、转交、结束和建议生成禁用。

采用浅色、蓝灰为主的高信息密度工作工具风格；红橙只表示风险、失败和待处理。不使用强 AI 视觉符号或大面积渐变。所有状态不可只依赖颜色，需适配系统字体缩放并保证触控区域和辅助文本可用。
